# 角色库 V0.3：最小疲劳与恢复

本版在 V0.2 的发力建立之前增加一个疲劳状态。持续抵抗时可用能力缓慢下降，负载降低或比赛暂停后逐渐恢复。`demo` 的疲劳参数和建立时间常数均为 0，输出与原控制器相同。

人物编号、年龄、性别、训练背景以及原刚度、阻力上限、建立常数均沿用 V0.2。下列参数由人工指定，只用于展示模型变化，没有按人物属性推算，也没有经过人体或制动器标定。

## 参数和计算顺序

| 人物 | 疲劳率 a，1/s | 恢复率 b，1/s | 最大能力损失比例 l | 建立常数，s |
|---|---:|---:|---:|---:|
| demo | 0 | 0 | 0 | 0 |
| person_01 | 0.06 | 0.12 | 0.50 | 0.15 |
| person_02 | 0.04 | 0.10 | 0.45 | 0.40 |
| person_03 | 0.03 | 0.08 | 0.40 | 0.80 |

`common/characters.py` 保存每个人物的 `FatigueParameters`，三个参数都校验为有限值且在 [0, 1]。疲劳率、恢复率的上界是本演示程序的配置约束，不是人体生理范围。模型状态独立保存在 `common/fatigue.py`。

```text
M_base = 原角度控制律计算的静态幅值
u = clamp(M_base / max(人物阻力上限, 1e-9), 0, 1)
df/dt = a*u*(1-f) - b*(1-u)*f
capacity = 1 - l*f
M_eligible = M_base * capacity
M_output = V0.2 发力建立模块更新(M_eligible)
```

`f` 为 [0, 1] 的等效疲劳，capacity 为剩余能力系数。`u` 是静态目标相对人物上限的负载代理量，不是肌肉激活、肌电、实测用户力或制动功率。即使角速度为 0，只要静态目标不为 0，模型仍可能积累疲劳；实际有符号制动力矩仍由原 `passive_torque()` 决定，静止时为 0。

每个有效 tick 假设当前 u 在本次间隔内恒定，使用一阶方程的精确指数更新。负载突变时采用当前 tick 的值，不重建区间内的动作。dt 来自传入的单调时钟；重复时刻不积分，时间回退、非有限值、间隔超过 0.25 秒时跳过该区间。故障或切换状态会丢弃计时锚点，恢复后的首个有效 tick 只建立新时间基准，避免补算未知时段。

疲劳和建立幅值分别保存。输出始终满足 `0 <= M_output <= M_eligible <= M_base`。目标降低时建立模块立即跟随上限，自由区为 0；有符号力矩乘角速度不大于 0。模型没有主动驱动机械臂的分支。

## 按钮、回合和异常如何处理

| 状态或操作 | 制动与建立幅值 | 疲劳 |
|---|---|---|
| running | 正常计算，非 demo 从 0 缓升 | 按负载代理量变化；低负载可能恢复 |
| 同一人物 paused | 立即 STOP/0，清除已建立幅值 | 有效遥测和 VR 心跳持续正常时，按 u=0 恢复 |
| waiting | STOP/0，准备下一回合 | 确认人物并归零；重复心跳归零结果相同 |
| 同一人物 finished | STOP/0 | 保留并冻结，下一次 waiting 归零 |
| 设备故障、遥测/VR 超时、断开 | 优先 STOP/0，清除建立幅值 | 保留并冻结，不假定人在休息或继续发力 |
| 故障恢复后 running | 非 demo 重新从 0 建立 | 保留故障前疲劳，不补算断联时间 |
| 非 running 确认不同人物 | STOP/0 | 新人物从 0 开始，不保留每人的跨回合档案 |

直接从 finished 回到 running 会沿用该人物疲劳；需要新回合时先发送 waiting。paused 同时承担原协议允许的确认选角功能，选择其他人物会重置为新人物。running 中换 ID 仍保持当前人物；未知编号仍解析为 demo，不能绕过运行锁定。断开或进程重启后没有持久化疲劳；重启 PC 为新状态。

暂停恢复是软件的休息假设，不代表用户确实放松。暂停期间若发生机械或 VR 超时，故障优先级更高，恢复计时随即冻结。暂停/故障消息即使在两次计算之间被后续消息替换，也会清除建立幅值并中断疲劳计时。

## 30 秒时间序列

运行仓库根目录下的命令即可生成，不需要 Unity、COM 口或额外 Python 依赖：

```powershell
.\.venv\Scripts\python.exe tests/characters/fatigue_table.py --output fatigue-response.csv
```

已保存的 [CSV](test-results/2026-11-17-fatigue-response.csv) 共 1204 行，四个人物各 301 个时刻，间隔 0.1 秒。它调用真实共用 `BridgeState`，同时用原建立模块计算 V0.2 无疲劳参考值。遥测速度固定为 −0.2 rad/s；0–12 秒角度 −0.4 rad，12–16 秒减为 −0.26 rad，16–22 秒 paused，22–28 秒恢复 running/−0.4 rad，28–30 秒 waiting。分段起点计入新阶段；比赛状态切换首个 tick 不跨状态积分。

## 通信与使用

`common.bridge` 和 `real.run` 继续复用 `BridgeState`，启动命令见 [README](../README.md)。UDP V0.1、端口、串口 V1 帧及字段均未修改，VR 仍只需发送 character_id 和比赛状态。新增疲劳数值不进入 Unity 数据报或串口帧。

PC 本地状态/JSON 日志增加 `fatigue_level`、`fatigue_capacity`、`fatigue_load_proxy`、`eligible_target_torque_nm`。原 `base_target_torque_nm` 仍为静态目标，`target_torque_nm` 为当前建立后下发幅值。停止时这些目标幅值均为 0，疲劳值可能保留。中文面板显示“等效疲劳”“剩余能力系数”“疲劳后目标”，均标注为模型演示值。

正式 VR 客户端和现有 Unity C# 脚本无需修改。测试目录的 Python Unity 验收脚本更新了幅值条件：检查原静态目标和动态输出范围，不再要求疲劳人物持续达到静态目标。

## 测试与遗留

Windows 本机的最终验证结果记录在 [测试摘要](test-results/2026-11-17-characters-v03.json)。单元测试覆盖疲劳范围、实际 dt、重复/回退/异常时间、下降和恢复、demo 精确回归、所有停止分支、回合重置与人物锁定；串口测试保留了原 225 mN·m 精确编码参考，并检查实际动态幅值的编码。

- 相关 Python 回归共 84 项：83 通过，1 项 Linux PTY 专用测试在 Windows 跳过。运行命令保存在测试摘要，可在仓库根目录复用。
- 本机 Unity `2022.3.62f3c1` 实际进入已有场景 Play，33 项检查全部通过。包括 C# UDP 双向收发、原五/六字段集合、人物锁定与确认、动态幅值范围、角度映射、遥测断开 STOP 和暂停归零。原始结果在仓库同级 `UnityUdpDemo/TestResultsCharactersV03/`；未用 Python 模拟 VR 代替。
- 本机 ELTIMA `COM1 ↔ COM2` 实际 V1 线缆模拟检查 6 项通过，覆盖握手、CRC、命令/遥测、序号回绕、看门狗和重新会话。这是软件 COM 对及模拟设备，不是真实 STM32；疲劳动态幅值的 V1 编码由串口内存链路测试单独覆盖。
- 额外执行全量 `python -m unittest discover -q`：83 通过、1 跳过、8 错误。安装仓库已有 `requirements.txt` 后，MuJoCo 3.17.0 在当前 Windows/Anaconda 虚拟环境仍发生 DLL 初始化失败（WinError 1114）。错误涉及 `MujocoDynamicsTests` 两项及 `test_direction`、`test_fit_analysis`、`test_horizontal_grip`、`test_mechanics`、`test_operator_layout`、`test_visualization` 六个模块导入。没有修改这些模块或将错误改成跳过，全量测试不能称为通过。

本版参数尚需与真实设备输出、体验反馈和之后采集的数据校准。当前只有一个等效疲劳状态，没有独立疲劳阈值、肌肉模型或持久化档案。真实 VR 场景、STM32 和制动器尚需各组联调；这些接入不必等待继续完善疲劳模型。
