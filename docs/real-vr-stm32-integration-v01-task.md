# 下一阶段任务：真实 VR / STM32 联调 V0.1

> **待实施任务书，不代表真实硬件已通过测试。** 基于人物角色库 V0.3 提交 `d4c6513`，当前重点从“继续加人物模型功能”转为“把已实现的软件接入真实 STM32 与 VR 场景”。可按设备到位情况分段完成，任何一条线都不必等待另一条完美。
>
> 代码原则：优先保持现有 Python 控制层、`docs/vr-udp-v01.md`、`docs/stm32-serial-v1.md` 不变；如联调发现确实不匹配，记录对端反馈，双方约定后再修改。不要为了联调引入新的神经网络、人物类型、重型框架或完整 UI。

## 当前已有的依据

- PC 共用角色/控制状态：`common/control.py`、`common/characters.py`、`common/strength_response.py`、`common/fatigue.py`、`common/state.py`。
- PC 正式串口 + Unity UDP 入口：`python -m real.run --port COMx`；需要 `pyserial`。其与模拟 TCP 入口 `python -m common.bridge` **只能二选一**，都占用 UDP 9102。
- `docs/stm32-serial-v1.md` 是给 STM32 组确认的 **V1 修订草案**，明确二进制帧 `A5 5A`、`CRC-16/CCITT-FALSE`、会话 OPEN/ACK、主轴侧目标阻力单位 `mN·m`、遥测角度 `mrad` 和速度 `mrad/s`。
- `docs/vr-udp-v01.md` 是 Unity/VR ↔ PC 的 UDP JSON V0.1。VR 发送 `character_id`、`match_state`；PC 发送 `angle_rad`、`mode`、`reason`（另有协议 `v/type/seq`）。
- Windows 软件验证：角色库 V0.3 相关 83 项 Python 测试通过/1 PTY 跳过；Unity C# UDP 33 项通过；模拟 COM V1 6 项通过。**都不等于真实硬件或 PICO 验证**。Windows MuJoCo DLL `WinError 1114` 是独立环境问题，当前联调无需先修好。
- `tests/unity/` 仅是测试代码，正式 VR 由 VR 同学维护，不能要求他拷贝完整的测试场景。

## 先完成两个互不阻塞的联调分支

### A. 与 VR 同学：正式场景 UDP

1. 把协议 `docs/vr-udp-v01.md` 交给 VR 同学，让他在自己的 Unity/团结引擎项目里按相同 UDP JSON 消息实现通信；`tests/unity/ArmWrestlingUdpClient.cs` 仅为可选参考。
2. 先在同一 Windows PC 或可信局域网，用 **PC + 模拟 STM32** 快速联通，测试四种 `match_state`、人物编号、合法角度、`angle_rad=null`、Stop/Play、VR 心跳超过 1 秒的超时与恢复。
3. 重点确认机械零位、向获胜方向下压时 `angle_rad<0` 的映射、虚拟手臂转轴及零姿态；**角度能驱动动画** 不等于手柄在世界坐标中已空间对齐。
4. 如果 VR 同学使用另一台设备或 Android/PICO：`127.0.0.1` 只指向各自本机，需明确 PC 局域网 IP、PC UDP 绑定地址及防火墙；只在可信局域网测试，测试端口不直接暴露公网。PICO/Android/IL2CPP 兼容性必须另行实测，不以现有 Unity Editor 结果代替。
5. 留下最简证据：运行环境、两个端点地址/端口、角色选择示例、角度变化、暂停/断联行为与未完成事项。**不更改正式 UDP 字段**，除非双方明确决定升版。

### B. 与 STM32 同学：先串口后制动

1. 请下位机组对照 `docs/stm32-serial-v1.md` 核定：USB CDC 还是 USART+USB转串口、端口与 115200/8N1（如适用）、小端数据、CRC16、会话 OPEN/ACK、遥测标志位、命令序号和看门狗；同时明确固件现已实现哪些功能。先验对照需简短，不要无限期审查。
2. **首次接实体板，先不连接真实制动器励磁功率或人手**，仅让 MCU 输出模拟/真实编码器角度遥测，验证 PC 使用 `python -m real.run --port COMx` 能打开、握手、正确解析角度/速度及状态。选角仍可由模拟 VR 或 Unity 发送，无须同时测试所有模块。
3. 逐项核对零位、角度正负、单位 `mrad`、速度换算、遥测刷新及故障标志。PC 下发的 `target_torque_mnm` 是**主轴侧无符号目标阻力**；`applied_target_mnm` 只是 STM32 限幅后的目标值回报，**不是实测机械力矩**。
4. 在**无人员接触的台架**、有物理急停/机械限位/独立电流与力矩保护且由电气组确认的条件下，再接制动器驱动。先检查 STOP、急停、故障、USB 拔插、PC 程序被杀、命令超时、旧会话重复帧均不能继续输出危险阻力；人工重新使能必须独立于 VR `running` 和串口握手。软件模拟的 `--demo-arm` 绝不能用于或推导实机许可。
5. 再使用低风险、经硬件组确认的台架工况进行电流→制动器轴侧抗转矩→主轴侧抗转矩标定，检查 4:1 传动、损耗、低速/零速特性。记录实际测力、有效力臂、换算和不确定性。**不要用目标指令或电机额定值冒充实际测量**。
6. 设备本地保护、限幅、独立使能和标定完成之前，不进行人与装置直接对抗实验。后续体验测试需单独制定安全条件和场景。

## C. 两条线都接通后再做合并联调

路线为 `实体 STM32 → PC real.run → VR 同学正式场景`。从 `demo` 基线与 waiting 开始，再尝试 V0.3 三个人物；检查角色锁定、缓升、疲劳、暂停/结束、断联与重启。在日志区分 `M_base`、疲劳后目标 `M_eligible`、PC 下发 `M_output`、MCU 回报目标和**台架实测力矩**。结果不能仅凭画面运动或数值回报认定真实阻力已经正确。

## Codex / 联调交付

- 首先读取本文件、当前 GitHub 代码、STM32 与 VR 的协议文档；安全保留工作树。
- 当外部组尚未准备好时，整理**双方各需提供的最小接口信息与测试步骤**即可；不要伪造“实体板联调通过”或写大量占位代码。
- 当有真实设备可用时，在 Windows 按顺序实际测试，记录具体 COM 口、固件版本/提交、Unity 工程版本、协议不一致点、控制状态和日志，并尽量优先修真正阻断联调的问题。
- 如需改代码，只修改最小相关部分，保持 V0.3 角色模型和 `demo` 的回归结果，运行相关测试后提交 GitHub，返回 SHA。
- `WinError 1114` 所涉 MuJoCo 环境问题单独记为待办；除非开始依赖 MuJoCo 的工作，否则**不阻塞本阶段交付**。

**完成标志：** VR 正式场景已通过实际 UDP 交互验证，或实体 STM32 已完成安全隔离条件下的真实 V1 串口互通；每完成其中一项，就能形成可交接的小阶段成果，不要求所有硬件一次到齐。
