# STM32 联调工具 V0.1：交互式模拟 VR + 串口诊断（2026-11-27）

## 1. 目标与基线

下位机同学应能在自己的 Windows 电脑上，不安装 Unity/PICO、不理解控制算法代码，只用一个轻量中文界面完成选人物、选策略、比赛开始/暂停/继续/结束、观察遥测和目标阻力、诊断串口及保存日志。目标是让联调独立于 VR 美术工作，而不是另做一套控制系统或通用串口助手。

- PC 仓库 Ihtbfas/armwrestling，已收口基线 `9018dc2c8d7d3f7cd32e711c27a02908f71d029e`。本任务分支从该提交创建。先检查实际本地工作树及远端，保留用户已有改动；若基线更新，核对后采用兼容版本。
- 现有入口 `real/run.py`（串口）、`real/stm32_link.py`（会话/帧收发）、`common/serial_protocol.py`、`common/state.py`（所有控制策略）、`common/console.py`（JSONL/终端）、`sim/mock_vr.py`（仅 CLI 心跳）、`sim/mock_stm32.py`、`sim/mock_stm32_serial.py`。优先复用。
- 先读 `docs/stm32-serial-v1.md`、`docs/vr-udp-v01.md`、`docs/real-vr-stm32-integration-v01.md`、`docs/character-library-v05c.md`。串口 V1 仍需下位机组确认，并未取得实体板联调结果。
- 控制基线、人物参数、默认 legacy+symmetric+0 ms、UDP V0.1 和串口 V1 字节格式均不改。不再扩展算法，不修改正式 VR 仓库、固件、机械仿真、硬件驱动。现有 CLI 和自动测试继续可用。实验 narrow/relief/延迟不得通过新工具开放到实体串口。

## 2. 界面与操作流程

建议 Python Tkinter/ttk 中文桌面工具（Windows Python 自带 GUI 组件需检查，外部依赖尽量只有 pyserial），独立入口如 `python -m tools.stm32_debug`，可附一键 PowerShell/bat 启动。入口命名按实际仓库组织调整。先做功能清晰、可实际操作的窗口，不引入 Web 服务、Electron、复杂绘图库或安装程序。EXE 打包不是本轮必需。

### A. 连接设置和测试类型

- COM 下拉与刷新（serial.tools.list_ports，显示实际设备描述），波特率默认 115200，8N1。选择设备、连接、断开。不得自动认定某个 COM 就是实体 STM32。
- 默认进入“串口通信检查/仅 STOP”模式：未握手发送 OPEN；匹配 ACK 后只请求 STOP/0，不允许界面进入 running，也不允许其他 UDP 客户端使此模式变成 ENABLE。建议给 real.run 添加独立的本地可选 monitor-only 门（默认 CLI 行为保持），或采用等效后端硬门控；不可只依靠按钮禁用。此模式不是纯只读串口，因为会主动握手及发送 STOP。首次接板必须由下位机/电气组确认制动器励磁功率物理隔离、无人接触设备。
- “模拟 VR 比赛”模式：同一 PC 真实串口入口、正常控制状态机，GUI 通过原 UDP 心跳代替正式 VR。该模式可能产生非零目标阻力，默认未选中；用户明确选择后才能进入比赛。首次验证仍在无励磁功率、无人体的条件下进行，固件本地 READY/ARM_READY/故障/会话/看门狗等独立规则始终有效。界面没有解除急停、清故障、自动重新使能、强发任意力矩/PWM/电流等功能。
- 若实现成本很低，可增加“纯软件预演”，复用 common.bridge + sim.mock_stm32，自动启动或说明手动启动；不需要虚拟串口驱动、Unity 或 MuJoCo。真实串口协议的验证仍用已存在的虚拟 COM 对或实体板，不能用 TCP 预演结果冒充 V1 验证。不要为此额外设计模拟机械或复杂 GUI。
- 本地调试使用 127.0.0.1 和独立可配置的 UDP 端口（建议 19102），不要干扰正常正式 VR 9102，也不需要广播、公网服务。检查端口占用，只管理本工具创建的子进程；不得关闭无关程序。

### B. 模拟 VR 比赛

- 人物从 common.characters 读取 demo、person_01/02/03，显示示例资料及虚构演示参数；显示请求与 PC 实际生效人物，不把年龄/性别当成策略。
- 策略从 common.strategies 读取均衡 balanced、防守 defensive、节奏 rhythmic。当前 PC 的 --strategy 是进程启动参数，V0.1 只允许连接前选择或停止比赛后明确断开重连再选择；界面提示重新握手及可能需要设备侧重新授权，不在 running 时热切换，不修改 UDP 加 strategy_id。demo 始终原基线，界面注明策略不会改变 demo 输出。
- 按钮：准备/开始（可选简单 3 秒倒计时，倒计时仍 waiting）、暂停、继续、结束、再来一局（waiting 清疲劳，不执行真实机械回零）。默认 waiting。保留现有角色确认/锁定规则；界面仅在非运行时允许选角。状态变化及时发送完整 vr_update，正常每约 200 ms 发送，seq 单调增加，同一 socket 收发。
- 可显示简洁角度/推进量表盘或指示杆、比赛用时。若做自动胜负，使用与 P3.0 正式 VR 一致的演示映射（机械负角获胜，±25° 机械判定、0.35 s 有效保持、60 s 时限）；阈值是软件演示值而非机械安全限位。只使用新鲜有效测量；空角度、stop/故障或过期不能继续判胜；不要求自动胜负作为首次串口验收，手动结束亦可。
- 真实串口比赛开始/继续前检查有效会话、遥测、本地许可及无故障。若条件不满足，等待/显示原因，不要求固件为了通过而强行 ARM_READY。收到故障、遥测/PC 超时、GUI 暂停失活或后台退出时撤销正常比赛状态，恢复后需要显式人工继续。禁止后台心跳无限发送陈旧 running。合法 0 与 null 明确区分，模式 STOP 时有效角度仍可显示。
- 保留 PC、下位机看门狗机制。界面停止仅为比赛停止/目标归零，不叫硬件急停；退出先尽力发送非 running 状态、停止心跳、正常关闭自建后端，再由独立下位机看门狗处理失联，不能承诺关闭窗口会让机械停止或立即断电。若工具进程异常退出，不得留下无限 running 心跳；PC 失联超时正常生效。

### C. 实时诊断区（优先于美术）

同一个窗口清楚显示：
- COM/连接是否打开、SESSION_OPEN/ACK 是否匹配、会话编号（十六进制）、有效遥测是否新鲜、实际报文接收速率/年龄；区分“串口打开”“已握手”“有遥测”“本地已授权”四层，不用一个绿色灯概括。
- 原始 status_flags 十六进制及 READY、ARM_READY、FAULT、ESTOP、LIMIT、ACK_VALID、FORCE_VALID 各位解释。未获 ARM_READY 不等于协议失败。
- 角度（rad/deg、机械负角获胜）、角速度、有效测力 N（FORCE_VALID=0 显示未提供）；请求/生效人物、策略、比赛状态、停止原因、等效疲劳。
- PC 算出的目标幅值、实际成功完整发送的最近一条串口命令（STOP/ENABLE、mN·m、线序号、有效期）、STM32 回报已接受的 last_command_seq（ACK_VALID=1 才有效）、applied_target_mnm（换算 N·m）。计算、完整发送、MCU 已接受、MCU 目标回报是不同层次。不要把最后分配/入队的 tx_seq 当成功发送，不把回报目标当实测力矩。串口接收状态过期时标记最后读数失效。
- 简单滚动日志与实时角度、PC 目标/MCU 目标折线或文本值；初版先保证数字和事件准确。可选“通信详情”展示少量最近实际收发的十六进制帧、长度、类型、CRC/非法头/重复旧序号/组帧超时计数（按真实记录定义）。当前 FrameParser 会直接丢弃坏帧，尚无完整错误统计；若实现计数，只在现有 parser/adapter 增加观测，不能编造或更改解析行为，未知/未实现显示“未提供”。不要默认把高频原始字节刷满 GUI；节流、有限缓存、可导出。
- 一键保存本轮 JSONL/CSV 或日志目录，包含版本、设备、配置、相对时间、事件及原始记录。显示“疑似哪层出错”的简短排查提示：未打开 COM / 无 ACK / ACK 正常但无遥测 / 未授权 / 目标已发但 MCU 未确认 / 设备回报与目标不同 / 设备异常。实际 MCU 目标可能因本地限幅、时序或无效 ACK 不同，不能仅凭一个瞬时差值定性固件故障。

## 3. 推荐实现方式

- GUI 是现有 PC 后端的轻量操作面板，不自行重写控制计算/串口解析。优先让 GUI 通过 subprocess 调用现有 real.run --display json --log-file ...，并独立使用原 UDP V0.1 发送模拟 VR 状态；也可复用现有 serve 函数做单独后端工作线程，选择最简单且可可靠关闭、隔离阻塞的方式。不要使用 shell 字符串拼接参数；COM、日志路径、策略等验证后传参数数组。
- 扩充 real.run 的本地结构化诊断与 Stm32Link/FrameParser 的必要观测字段，现有基础 JSON、控制路径和正式 UDP/串口保持兼容。现有快照约 0.5 s 一次；根据界面需要可加显式本地诊断刷新选项（例如 5–10 Hz 受控快照），不改变控制周期；如果原有快照足够，不额外提高。帧级采样应异步或有界节流，不让 GUI、日志渲染、输出管道或绘图阻塞串口控制循环。
- GUI 主循环用 after 等非阻塞方式处理心跳、控件和诊断队列。后台读取仅传入数据，不直接操作 Tk 控件。子进程异常、串口拔插、超时、PC 重启、GUI 关闭后状态可靠回退；禁止自动恢复 running。模拟 VR 状态机及数据处理尽量做成可独立测试的小模块。
- 本轮不新增自由格式报文注入/任意 ENABLE 按钮或故障绕过；现有协议黄金样例与软件虚拟端口测试用于诊断，不在 GUI 默认向实板注入错误帧。若日后需专门的制动标定模式，待硬件独立保护、实际限幅和台架方案确认后另做。

## 4. 验收与交付

1. Windows 实际打开中文 GUI，截图说明连接、通信检查、模拟比赛、日志页。无 Unity、无 MuJoCo，安装 pyserial 后可运行。串口列表刷新/占用/打开失败有明确提示，界面不卡死。
2. 使用现有软件虚拟 COM 对和 sim.mock_stm32_serial 验证真实 V1 字节链路（例如本机 COM1↔COM2，按实际端口，不写死），仅在模拟端使用 --demo-arm。实测默认通信检查即使有运行请求仍不发 ENABLE；展示合法 0、有效遥测、未授权与故障、握手、各状态位、命令发送与 ACK/回报。至少两个非 demo 人物/不同策略的实际选择与 PC 生效结果，完成开始、暂停、继续、结束、waiting 新一局；策略切换不跨回合暗改。
3. 断开模拟设备/关闭后端、GUI 失活或退出、重启后端，检查 stale/null、停止心跳/STOP、重新连接后等待且不自动恢复比赛。软件虚拟端的实际指令记录用于证明停止行为。可以在隔离虚拟链路上用已有测试覆盖 CRC、分包、重复序号，核实新增诊断计数；不为展示故障而攻击实际板。
4. 回归原 Python/串口协议/控制默认、所有老入口；无需反复运行 Unity/PICO/MuJoCo。硬件未到位时不宣称实体联调完成。
5. 简明给下位机同学使用的中文 README/指南：Python 版本及 pyserial 安装、启动命令/脚本、操作顺序、四层连接诊断、保存日志位置、典型问题及测试范围。提交真实 GUI 截图（不含私有个人信息）、虚拟 COM 验证记录、代码和 SHA。推荐在独立工作分支交付。遇到局部问题自主解决，先完成最小可用工具，不做无必要框架或长期重构。
