# 角色库 V0.1：Windows Codex 实施任务

> 目标：先建立**最小可运行**的人物角色库，并用现有 PC 阻力控制与 VR UDP 联调验证。不要将本任务扩展成完整的人体肌肉模型；后续还需要 VR、STM32 和实物联调。
>
> 状态：已实现 V0.1（2026-11-16）。Windows Python 测试 56 项通过、1 项 Linux PTY 测试跳过，并完成真实 TCP/UDP 三进程演示。人物定义、选角规则和验证范围见 [实现说明](character-library-v01.md)。下文保留原实施要求。

## 1. 项目与环境

仓库：[Ihtbfas/armwrestling](https://github.com/Ihtbfas/armwrestling)。

本项目是被动磁粉制动器的单自由度扳手腕装置。PC 接收摆臂角度和角速度，计算阻力幅值，向 STM32 下发指令，并通过 UDP 向 Unity/VR 返回机械角度和运行状态。

当前用户在 **Windows**，已经有可以运行的 Python 和 Unity 编辑器。本阶段角色库主要使用 Python 标准库，**不依赖 Ubuntu、Linux PTY、MuJoCo、头显或真实 STM32**。Windows Unity 已通过基本 UDP V0.1 联调。

重要文件：
- `common/control.py`：当前纯阻力计算 `BrakeParameters`、`brake_state`；**保留原函数及默认行为**。
- `common/state.py`：状态协调、`BridgeState`；当前仅记录 `character_id`，尚未据此改变阻力参数。
- `common/bridge.py`：模拟 STM32 TCP 9101 + Unity UDP 9102 PC 入口。
- `real/run.py`：未来真实 STM32 串口 V1 + 同一个 Unity UDP 9102。
- `docs/vr-udp-v01.md`：与 VR 同学已经约定的协议，**本阶段不要改字段**。
- `sim/mock_stm32.py`：Windows 可运行的模拟运动数据源。
- `tests/unity/`：我们的自测 Unity 代码，不是 VR 同学必须采用的正式组件。
- `common/test_bridge.py`：已有桥接及状态测试。

目前基本控制律为：`q = -(theta - 0)`，`M = min(Mmax, K * max(0, q - 0.25))`；默认 `K=2.0`、`Mmax=0.8 N·m`。控制系统是被动阻力，不能主动推动用户的手臂。模拟和实机安全边界不能混同。

## 2. 本阶段要做的事

### A. 建立最小角色库

以 `character_id` 为键，定义 **2～3 个示例人物 + 原来的 `demo` 基线**。每个人物包含：

- 角色 ID / 用于调试的显示名称
- 年龄、性别、训练背景等**人物信息**
- 当前可执行的基础阻力参数，例如刚度和最大目标阻力

**人物的定义依据是年龄、性别及训练经历等属性，不要把“爆发型、耐力型、防守型”当作人物身份。** 发力策略库是后续独立扩展的模块。

目前没有真实的年龄/性别→扳手腕力矩参数标定，因此示例人物的控制参数只能标注为**演示值**，不得宣称是特定人群的平均力量或反映确定的性别、年龄因果关系；人物之间可能有很大的个体差异。优先选取能够在现有模拟角度行程内表现出区别、同时不超过原基线演示上限的参数。不要引入“年龄性别必然决定强弱”的规则。

建议角色库集中于一个简单、易读的 Python 模块（例如 `common/characters.py`），未来可以直接换成有文献或实验依据的参数。不要建立数据库、网站或复杂配置框架。

### B. 让角色选择真正影响 PC 控制

保持现有 `common/control.py` 的基础算法和所有默认参数不变，只在状态协调处根据收到的 `character_id` 选择对应的 `BrakeParameters`。

- `demo` 必须严格保持过去的控制输出，防止旧版测试回归。
- 未识别的角色 ID 采用明确、安全的回退行为（例如默认 `demo`），**在 PC 日志中可辨认**，不能因此崩溃或输出超出上限。
- 防止比赛过程中切换人物时瞬间出现不受控的阻力跳变。V0.1 可以采用最简单的规则：只在比赛处于非 `running` 状态时确认新角色，然后整个正在进行的回合使用已选角色；如果代码结构允许，也可采用等效的简单处理，但不要扩展复杂平滑框架。
- 不要破坏停止、遥测超时、VR 心跳超时、设备故障和旧消息序号检测。**故障保护优先于人物策略**。
- 如果控制器未来用真实硬件，必须再次遵守硬件标定后的全局安全上限；此版只是模拟控制，不能声称已验证人员安全。

### C. 测试与展示

使用 Windows 上可直接运行的 `unittest`，至少验证：

1. `demo` 与旧版本输出一致；
2. 不同人物在**相同角度和角速度**下得到可区分的阻力；
3. 按 `character_id` 选中对应人物，未识别 ID 不会导致失控；
4. `paused / waiting / finished`、设备故障、遥测过期、VR 过期仍停止正常阻力；
5. 人物选择不会改变 `docs/vr-udp-v01.md` 的 UDP 报文字段。

可增加一个非常简单的对照输出（终端表或 CSV/PNG 中择其一），展示不同人物在同一组角度下的目标阻力。不必为此增加复杂依赖；若需要画图，优先使用已有环境。

建议 Windows 先跑：

```powershell
python -m unittest common.test_bridge -v
python -m common.bridge
# 另一个 PowerShell:
python -m sim.mock_stm32
```

如果还要用 Unity，采用现有 `UnityUdpDemo` 或 `tests/unity/` 中的测试程序，检查从 `character_id` 选择人物后，PC 本地日志中的目标阻力确实变化。**不要要求 VR 同学修改现有协议或正式场景**；可以用自己的模拟 UDP 客户端完成角色选择验证，也可以在测试工程中调整角色编号。注意不要同时启动两个 VR 客户端抢占 UDP 源端口。

## 3. 现在明确不做的事

- 暂不建立完整 Hill 肌肉模型、肌肉疲劳模型、神经网络、强化学习或详尽生理参数库；这些属于 V0.2 及之后的任务。
- 暂不改变机械模型、仿真物体、原有 UDP 字段、STM32 串口 V1 帧格式、真实固件、安全使能规则。
- 暂不新增正式 Unity/VR 代码；测试代码继续与正式 PC 程序解耦。
- 不因为角色库尚不完善而阻塞其他组员的 VR、下位机联调。

## 4. Codex 工作方式与交付要求

1. 先看本地仓库的 `git status`，阅读必要的源码和本文件；如需同步 GitHub，请避免覆盖未提交的本地更改。
2. 自主选择简洁可读的 Python 文件组织方式；以**最少修改完成 V0.1**，不要长时间停留在前期方案审查。
3. 先在 Windows 本地运行核心测试与最小通信演示；如果某项 Windows GUI 操作只能由用户完成，给出清晰步骤。
4. 更新少量必要说明，特别标注演示参数并非人体实验数据；提交并推送 GitHub（尽量保持 `main` 快进），反馈 SHA、文件位置、测试结果、示例人物差异和待解决问题。
5. 后续 V0.2 的肌肉激活/疲劳模型和 VR/STM32 联调可以继续迭代，**本阶段不要一步到位**。

**完成判据：** 在 Windows 上，可依据 Unity 或模拟 VR 已有的 `character_id` 选择不同人物，PC 计算出的阻力参数发生预期变化；原 `demo` 行为、通信协议和故障停止逻辑保持不变。
