# 人物角色库 V0.3：最小疲劳与恢复模型（Windows）

> **待实施任务，不代表代码已完成。** 基于 V0.2 提交 `10a368f3a68f722363e974c85f70cecf76f63ceb`。仅做一个小的时间状态扩展，能够运行就交付。其他组的 Unity/VR、STM32 与真实制动器联调优先级不低于本任务，可随时并行。

## 项目现状与职责边界

- 仓库：`Ihtbfas/armwrestling`；用户当前在 Windows，Python/Unity 已完成 UDP V0.1 双向联调。

- `common/characters.py`：`demo` + 三个按年龄/性别/训练经历描述的**虚构角色**。参数均为演示值，不从年龄/性别直接推导力量。
- `common/strength_response.py`：V0.2 的一阶缓升，只在升阻时缓升，降阻及时跟随；`demo` 不受影响。
- `common/state.py`：唯一共用的 PC 状态/控制入口；`common/bridge.py`（模拟下位机 TCP + VR UDP）和 `real/run.py`（STM32 串口 V1 + VR UDP）都复用它。
- `tests/unity/` 全部是我们的自测工具，VR 同学负责自己的 Unity 场景和程序。
- `docs/vr-udp-v01.md` 与 `docs/stm32-serial-v1.md` 是外部通信约定，本任务**不改字段、端口、帧格式**。
- V0.2 的实际 Windows Unity 选角验证：各 33 项检查通过；Python 66 通过、1 个 Linux PTY 专用测试跳过。实验数据见 `docs/character-library-v02.md`。

## V0.3 目标

**在 V0.2 之上，只增加“持续抵抗逐渐疲劳、低强度/休息可恢复”的最小模型。** 用虚构人物的两个或几个演示参数表现差异，继续保持年龄/性别等为人物身份，疲劳只是其身体能力参数；不要把“耐力型”当作角色身份。

建议以归一化状态 `f∈[0,1]` 表示等效疲劳。参考简单的演示方程（不是论文完整三状态模型，也不是实验标定结果）：

```text
u = clamp(M_base / max(M_character, epsilon), 0, 1)
df/dt = fatigue_rate * u * (1-f) - recovery_rate * (1-u) * f
capacity = 1 - fatigue_loss_fraction * f
M_eligible = M_base * capacity
M_output = V0.2 的发力建立模块按 M_eligible 更新
```

- `M_base` 仍由原角度控制律给出，`M_character` 是该人物在角色库中的目标阻力上限；`u` 仅为**模型内部的等效负载代理量**，不是实际测得的人体肌肉激活，更不能把它描述成真实人体的受力/肌电。
- 刻意简单：`fatigue_rate`、`recovery_rate`、`fatigue_loss_fraction` 均为演示参数，数值应使短时间曲线能看出区别但不过度突变；不使用年龄/性别计算它们。参数必须有范围校验。无需引入 Hill 模型、强化学习、神经网络或数据库。
- `demo` 继续**严格保持 V0.1 原输出**：疲劳关闭、V0.2 缓升也为 0。
- 所有输出必须满足 `0 <= M_output <= M_eligible <= M_base`，不提高原最大阻力；继续按照已有 `passive_torque` 确定运动方向，不能主动推动人手。
- `dt` 使用传入的单调时钟 `now`，不能假设固定 20ms；检测重复、回退、过长间隔，避免跳跃积分或在中断后自动累积大量疲劳。共用状态逻辑中谨慎组织，不复制 `bridge.py` 与 `real/run.py` 的控制算法。

## 状态处理：避免破坏现有联调

现有 V0.2 发力建立状态在暂停/停止时会归零。V0.3 **疲劳状态与发力建立状态应分开**：

- `running`：按当前模型负载积累疲劳，并计算发力建立；人物 running 中继续锁定，其他 ID 请求不得改变当前人物。
- `paused`：制动指令必须立即 STOP/0；发力建立状态清零。疲劳可以在暂停期间按简单恢复率逐渐恢复；恢复比赛仍需重新建立阻力。
- `waiting`：作为下一回合准备状态，允许确认人物，并将该人物的疲劳状态重置为新回合初值。若重复 waiting 心跳，不能造成异常。
- `finished`：输出 STOP/0，回合结束。明确约定疲劳保留或重置，保持可复现；建议下次 waiting 初始化。
- `fault/telemetry_timeout/vr_timeout` 等故障：**优先 STOP/0 和停止正常发力计算**；不得因恢复而突然使用过期积分得到高阻力。无有效机械输入时，不假设真实人体仍在维持某个已知强度。
- 非 running 时已有的人物确认规则保持不变，人物切换不会继承别人的疲劳。
- 注意 `paused` 在现有协议中既可用于暂停也可用于确认人物切换，保持 V0.1 行为，不额外新增 `reset` / `strategy` UDP 字段。

如果与现有 V0.1 状态语义有冲突，选择**最小且向后兼容**的实现，并在文档中明确解释处理规则；不要为了完美模拟而大改整个状态机。

## 测试与交付

1. 在固定角度（例如 −0.4 rad）和角速度（−0.2 rad/s）下模拟 10～30 秒，展示与 V0.2 的区别：先缓升；持续有负载时目标能力缓慢下降；暂停后恢复；再次 running 时重新缓升。用简单 CSV 或终端表足够，绘图可选。
2. 对 `demo` 精确回归；其他角色验证疲劳值区间、下降/恢复、同一时间重复调用、时钟异常和持续非负被动输出。
3. 保留人物锁定和切换规则，覆盖 waiting/paused/finished、遥测/VR 心跳失效、设备故障和新一轮状态复位。
4. 在 Windows 运行现有相关 Python 回归测试。允许快速跑一次 Unity 联调确保 V0.1 字段仍一致；**实体 STM32、PICO、人体或制动器测试没做就不要声称完成**。
5. 保持修改范围小、可读性优先；文档区分示例曲线、正式协议与实机限制。完成后提交并推送 GitHub，返回 SHA、测试结果、简短对照表及下一步遗留问题。

## 优先级

如果 VR 或 STM32 小组在此期间准备好联调，**可以直接暂停 V0.3 建模优先配合硬件和正式场景**。此模型不是硬件接入的前提。当前目标是获得一个可运行、可解释、可替换参数的最小版本，不是一次建完完整的生理模型。
