# P3.0：正式 VR × PC V0.3 联合仿真（2026-11-25）

> **待实施。** 本轮只解决正式 VR 与 PC 的兼容、完整对战闭环，以及可控的模拟用户施力。先完成可实际运行的联合仿真，再开始 V0.4 独立对抗策略库。不要把角色模型升级、人物美术、PICO 首测或实体硬件标定全部混进本轮。

## 1. 两个仓库与冻结基线

- PC：<https://github.com/Ihtbfas/armwrestling>，基线 `0729f9417df3b769f20ae9128710887201fc87ee`（角色模型 V0.3，已完成真实联调准备）。
- 正式 VR：<https://github.com/Ihtbfas/armwrestling-vr>，基线 `3f30bdb0d0afd7f2c40567c885a99126e4e251d6`（P2 离线模式收口，15 次实际 Editor Play；正式联网仍待验收）。
- 用户当前可用 Windows、Unity 中国版 2022.3.62f3c1；使用现有本机两个工作树。先查本机实际路径和 `git status`，不要覆盖未提交修改、原交付 ZIP、私有素材或本地标定资源。若仓库已更新，按实际新基线核对，不回退已有成果。
- 正式场景为 VR 仓库 `Assets/Scenes/ArmWrestlingMain.unity`。沿用 P2-D 默认公开 Rocketbox 人物、`LegacyHumanoidGrip`、共享机械握点、Animator/IK；不修改握姿、模型、肘垫、PICO SDK 或资产许可边界。P2-E 可选模式和各历史回退应继续可用。
- PC 共用 `common/control.py`、`common/characters.py`、`common/strength_response.py`、`common/fatigue.py`、`common/state.py`。保留 demo 基线以及 V0.3 原有控制公式、人物参数、自由区、疲劳/恢复和保护门控。当前不需要 MuJoCo、PICO 或真实 STM32。
- 两个仓库继续独立维护；正式 VR 网络客户端在 VR 仓库，PC 控制与模拟下位机在 PC 仓库。PC 的 `tests/unity/` 仅用于既有自测，不用它替代正式场景。

阅读 PC 的 `docs/vr-udp-v01.md`、`docs/character-library-v03.md`、`docs/real-vr-stm32-integration-v01.md`，以及 VR 的 `AGENTS.md`、`docs/P2-closeout.md`。以下源代码定位基于冻结提交，允许实际实施中作必要的小调整。

## 2. 第一小步：统一现有 UDP V0.1

正式 VR 的 Network 模式实际使用 `Assets/ArmWrestling/Scripts/Comms/VrUdpClient.cs`，不是历史二进制 `WireProtocol.cs / UdpDeviceConnection.cs` 路线。不要复活旧协议或把 STM32 串口协议套到 VR。

### 2.1 人物编号和界面语义

PC 已有 `demo`、`person_01`（24 岁女性、休闲运动）、`person_02`（38 岁男性、规律力量训练）、`person_03`（52 岁女性、有力量训练经历），均是虚构人物与演示参数。当前 VR 的 `OpponentRole` 为 Balanced / Defensive / Rhythmic，`ArmWrestlingApp.UpdateVrSessionState()` 与 `OpenConnection()` 发送 `opponent_01..03`。PC 不认识这些 ID，会回退 demo。

- Network 模式采用 PC 已有的规范 ID（person_01..03，并保留 demo 基线的测试入口），使实际 PC 日志显示相应生效人物。不要只改 ID 却继续把三个人物解释成均衡/防守/节奏策略。
- 建议把网络人物选择与原离线 OpponentRole 区分开，在现有 UI 上用最小改动显示对应人物资料；离线原策略和力量滑块保持可用。Network 模式中不要让未发送的 opponentScale 看起来会改变 PC 力量：禁用/隐藏该控件或明确注明仅离线有效。
- 本轮没有新增全部配套人物美术的要求；如复用 P2 的同一公开模型，说明其是联网测试占位形象，不宣称它已经对应真实年龄或性别。美术替换交给 VR 专门工作线。
- 先以 waiting 确认人物，再进入比赛；running 中角色锁定，切换规则与 V0.3 一致。未知 ID 仍按 PC 原规则回退。不要新加 strategy_id、年龄、性别或阻力参数到 UDP 报文。

### 2.2 比赛状态与方向

目前 `ToVrMatchState()` 把 Ready、Countdown、Fighting 都映射为 running。修为：

| VR AppState | UDP match_state |
|---|---|
| Boot / DeviceCheck / Calibration / Lobby / Ready / Countdown | waiting |
| Fighting | running |
| Paused | paused |
| Finished | finished |

准备和倒计时期间 PC 应持续 STOP/0、没有疲劳积累；新回合经过 waiting 复位，暂停恢复走原 V0.3 状态。只有正式开赛后才输出 running。确认选角的 waiting 心跳实际到达 PC，状态转换及时发送完整状态，仍保留约 200 ms 周期心跳。不增加一次性事件 ACK。

PC 机械角为 rad，负角表示我方推进；VR 当前客户端已通过 `-radians * Rad2Deg` 转为内部正向推进。实际配置资源 `Assets/ArmWrestling/Resources/ArmWrestlingConfig.asset` 方向为 +1、视觉缩放 1.2、视觉胜负阈值 ±30°、保持 0.35 s。保留这套当前演示设置，检查没有重复取反，机械 -25°（约 -0.4363 rad）对应视觉 +30°（不计滤波瞬态）。实际判定阈值与物理限位以后标定，不在本轮改控制自由区或真实机械范围。

### 2.3 网络健壮性（仅处理本轮明确的兼容缺口）

- 同机手动目标 `127.0.0.1:9102`，同一个 UDP socket 收发，每包一个 UTF-8 JSON。发送端可用 long 类型的非负递增 seq（与 PC 可接受范围一致），不再使用 ushort 回绕；接收端也用兼容整数。重复/乱序不续期，PC 重启/Unity 重连应可建立新会话并正确处理 seq 重置。先用显式地址，避免手动目标模式仍广播或被其他来源覆盖；跨设备/PICO 不作为本轮要求。
- 当前后台 Timer 心跳可能在 Unity 主循环暂停或失活时继续发送旧 running。确保心跳反映仍有效的应用状态，不因后台线程存活而无限维持过期 running；可采用简单的主循环心跳，或带主循环活性门控的方案。退出、暂停应用/失活（按实际运行环境区分桌面切换焦点与真正暂停）及停止 Play 时正确撤销正常比赛状态/停止发送。PC 既有 1 s 超时保持不变，不声称这替代硬件保护。
- 正确区分 angle_rad=null、数值 0、字段缺失、非法报文；不要只用字符串子串匹配 null 或把缺失字段的默认 0 当有效。可复用已验证参考客户端的解析思路，不必把整套测试脚本复制进正式工程。验证 v/type/seq/mode/reason 和有限角度后才刷新状态。
- PC 返回 stop 时可能仍有有效角度，画面可继续更新；但不能继续按旧角度累积胜负保持时间。Fighting 中遇到空角度、过期、设备异常或非预期 stop 时暂停并提示，恢复有效链接后由用户继续；刚进入 Fighting 时允许短暂等待新 enabled 状态，不把上一条 waiting/paused 回包当成新故障。所有情况下不凭无效数据、滤波残留或外推角度误判胜负；可使用有效测量角度换算的判定值、保持时间及新鲜度检查，动画滤波单独保留。
- UDP V0.1 不回传力矩或角速度。VR 端可保留明确注明的估算速度用于短时平滑；无力矩数据应显示“未提供”或隐藏，不把客户端的 0 当真实阻力。PC 日志仍是模型阻力、疲劳及生效人物的依据。
- 不改变既有 UDP 五个发送字段与六个返回字段、端口、STM32 V1 帧格式及 PC 保护规则。相关实现如已有更优简单方式可沿用。

## 3. 第二小步：可控模拟用户施力

现在 PC 的 `sim/mock_stm32.py` 是简化单自由度动力学：用户按 3 s 下压、3 s 回推、2 s 松手循环，制动幅值参与动力学积分。它与 VR 离线 `SimulatedDeviceConnection` 的主动对手力矩模型不同。正式 Network 模式以 PC 模拟 STM32 的角度为唯一机械输入，不叠加 VR 离线主动对手力矩。

增加一个明确的**仅用于软件模拟**的用户施力入口，优先最小实现：

- 保留原来的默认周期模式及其回归行为。
- 增加可选手动模式（例如 Windows 终端 1/2/0 或简短命令：下压 / 回推 / 松手，初始零用户力矩；可设几档有限模拟幅值）。不要阻塞遥测或控制循环，不需要全局键盘钩子/复杂 GUI。
- 增加可重复的输入试验方式，简单时间序列/脚本或独立测试驱动即可；使用同一输入比较不同人物，不依赖人工键盘时机。可在软件测试的新回合前提供明确的本地回零/复位步骤（不能将其解释为真实硬件回零，也不新增正式通信 reset 字段）。
- 真实目标仍由 PC V0.3 计算；模拟设备按当前速度应用被动制动，制动功率不为正。保留原模拟角度限制和看门狗，不因 VR 的离线力矩尺度而把 PC 的 0.8 N·m 演示上限扩大。
- 在模拟日志中记录用户输入力矩、角度/速度、模拟制动力矩和实际采用的控制命令；PC 日志记录人物、原静态目标、疲劳后目标、实际下发幅值和疲劳状态。注意它们都是软件数据。若只想让画面连贯，可以先不做复杂的人工输入曲线，最低要求是可手动施力/松手和可复现固定输入。

## 4. 第三小步：正式场景实际联合仿真

先在 Windows 本机启动两个 PC 仓库进程（旧进程如占端口，正常退出后再启；不批量杀无关进程）：

```powershell
# PC 仓库根目录，使用本机可用 Python
python -m common.bridge --log-file "$env:TEMP\arm-p3-pc.jsonl"
# 第二个终端，按本轮最终实现给出的手动模式启动方式
python -m sim.mock_stm32
```

Unity 中打开**正式主场景**，默认 P2-D，选择“改用网络数据”，或用现有 `-network -hostip 127.0.0.1 -hostport 9102` 命令行覆盖。不能同时启动 `sim.mock_vr` 或旧测试 Unity 客户端。首先使用 demo / waiting。软件模拟准备好后，再选三个人物做相同输入对照；不需要头显和实体板。

最低验收（允许自行修复实际阻塞问题，不逐项扩大需求）：

| 检查 | 通过标准 |
|---|---|
| 真正正式场景双向 UDP | 实际 Editor Play，PC 收到角色/状态，VR 接收真实 PC status；不是 Python 假 VR 或旧长方体 Demo |
| 选角及倒计时 | 三个规范人物均实际生效、不意外回退 demo；waiting/准备/倒计时 STOP/0 |
| 动作方向与完整回合 | 给已知机械正负角，人物方向正确；受控施力推动实际模拟机械，完成至少一次获胜/结束，测试另一侧结果与暂停继续；finished 后 STOP/0 |
| 角色差异 | 固定相同遥测角度/速度对照原 V0.3 动态阻力；同一可重复用户施力输入的闭环轨迹单独记录，不把不同角度时刻的阻力直接作为人物强弱比较 |
| 疲劳与复位 | 用足够长的有效软件负载（必要时独立固定遥测测试，不强行拉长正常比赛）观察疲劳；暂停归零输出、恢复重建、waiting 新回合复位 |
| 异常处理 | 模拟设备停止、null 与合法 0、VR 暂停主循环/Stop Play、PC 重启、重复旧包及序号边界；无错误判胜、过期数据不继续维持正常对抗；可重新连接 |
| 离线回归 | P2-D 默认离线选角、动画、倒计时、比赛和结算仍可用；保留原美术模式，不要求重新全量运行 P2 的 15 次组合 |

闭环试验中遇到手动施力使模拟回合过早结束，可调测试输入幅值与持续时间、从软件零位开始；不要为了过关悄悄改人物能力、胜负阈值或安全规则。输出实测 PC 日志及 VR 日志（按权限保留），至少一张实际正式场景截图/简短运行记录。公开画面仅使用有公开授权的资源，保留许可声明，原 Ch03 等不明授权素材和本机路径证据按 VR AGENTS 管理。

## 5. 范围与交付

- 建议在两个仓库各用独立工作分支，基于现有 main 最小修改；保留各自工作树与职责。分别提交并推送，提供两个 SHA/PR 及配对测试版本。若其中一个仓库暂不能操作，先完成能验证的小步并明确阻塞，不虚构联合验收。

- 最终提供最短 Windows 启动命令（含手动施力操作）、实际完整闭环结果、人物与状态证据、两仓库提交、未完成事项。按 `docs/real-integration-record-template.md` 记录为正式 VR + 软件模拟下位机测试；没有实体板、制动器或头显时，不声称它们已联调。
