# 人物角色库 V0.2：Windows 联调与发力建立模型

> 任务状态：**待 Codex 实施**。基于角色库 V0.1 提交 `7584f5f` 继续小步推进。本阶段不是建立完整人体肌肉模型，也不阻塞与 VR、STM32 同学的联调。
>
> 核心目标：**先验证 Unity 实际选角，再让人物的抵抗从“立即达到目标阻力”变成“逐渐建立阻力”**。必须保留 `demo` 原基线和安全停止行为。

## 一、首次接手先了解项目

- GitHub: https://github.com/Ihtbfas/armwrestling
- 用户当前在 **Windows**，已配置 Python 和 Unity，仓库可在本地运行。先检查 `git status`，在不覆盖用户未提交改动的情况下同步最新 `main`。
- 重要源码：`common/characters.py`（人物元数据和演示阻力参数）、`common/control.py`（基础被动阻力计算）、`common/state.py`（人物锁定、比赛状态、故障/超时门控）、`common/bridge.py`（PC 的 TCP 模拟下位机 + UDP VR）、`real/run.py`（串口 V1 + 同一 UDP VR）、`tests/unity/`（仅测试用 Unity 客户端）。
- 重要资料：`docs/character-library-v01.md`、`docs/vr-udp-v01.md`、`docs/windows-unity-udp-test.md`、`docs/stm32-serial-v1.md`。
- 当前 VR ↔ PC 使用 **UDP 127.0.0.1:9102**。VR 只发送 `character_id` 和 `match_state`（另有 `v/type/seq`），PC 只返回角度、模式和原因。**不得因人物模型扩展 UDP 字段**。
- 下位机真实接口是既有 STM32 V1 二进制串口协议；本任务**不修改串口协议或固件代码**。Windows 快速测试可用 `python -m common.bridge` + `python -m sim.mock_stm32`。
- 现有的人物 `demo`、`person_01`、`person_02`、`person_03` 都是**虚构人物与演示参数**。年龄、性别和训练经历是人物背景，不直接用于力量计算，不能宣称这些阻力值是某类人群的实测平均数。

## 二、第一小步：Windows Unity 选角验证

优先使用**已有** `UnityUdpDemo` 测试工程和 `tests/unity/ArmWrestlingUdpClient.cs`，不要改正式 VR 项目。

1. 让 PC 上位机与模拟 STM32 运行起来。Unity 端先以 `waiting` 发送人物编号，例如 `person_02`，然后切换为 `running`。
2. 看 PC 日志/面板里**请求人物与生效人物**是否一致，记录同一机械状态下人物的目标阻力变化。不要用不同角度时刻的阻力直接比较人物强弱。
3. 测试 `running` 中请求另一个人物不能立即换参数，切换到 `waiting/paused/finished` 后才确认新人物；`demo` 仍可用。
4. 如 Unity Inspector 改了人物编号但没有立刻生效，先检查脚本读入时机和当前 `match_state`，用已有接口验证，不为了这项测试修改已约定的 UDP 协议。
5. 如果当前 Windows 环境无法自动操作 Unity，给出最小手动步骤并**如实标注未实测**；不要让 Unity 验证成为下一小步实现的长期阻碍。

## 三、第二小步：人物发力建立 V0.2

V0.1 的静态目标仍由 `common/control.py` 根据角度、速度和人物阻力参数计算。**保留该纯函数及其默认行为**，在角色控制层增加很小的状态量表示“当前已建立的阻力”。

推荐最简单的一阶响应作为初步实现：

```text
M_base = 原有控制器计算的当前目标阻力幅值
alpha = 1 - exp(-dt / tau)   （tau > 0）
M_next = M_prev + alpha * (M_base - M_prev)
```

- `tau` 是**等效发力建立时间常数**，目前仅为演示参数；**不是已经实测的人类神经反应时间**。先不实现独立反应延迟、肌肉疲劳、恢复或策略库。
- 为尽量保持原有控制能力边界，V0.2 优先仅在**增加阻力时**按一阶响应缓升；当 `M_base` 减小时跟随减小、到自由区立即为零，避免旧目标残留阻力。Codex 可以依据现有代码选择等效且更清楚的实现。
- `demo`：`tau=0`，输出必须与 V0.1 原始控制器严格一致。
- 三个 `person_*`：赋予不同的演示时间常数，数值可由 Codex 在不引入额外安全风险和不夸大生理意义的前提下选择。**不得从年龄/性别直接推断时间常数或发力能力**。
- 在状态计算中使用实际传入的时间 `now` 计算 `dt`，不要假定每次都精确间隔 20 ms。相同时刻重复调用不应产生额外的发力增长；异常大的时间跳跃与数据过期不能造成无条件快速升阻。
- **暂停/等待/结束、VR/STM32 超时、设备故障、未就绪等，都必须立即输出原有 STOP / 0**，并合理复位/冻结人物内部响应状态，以免恢复运行时突然沿用先前积累的高阻力。
- 人物在 `running` 时仍锁定，人物切换必须遵守 V0.1 的 waiting/paused/finished 规则，且切换后不能继承另一人物的响应状态。
- 应始终满足 `0 <= M_next <= M_base <=` 已确定的演示控制上限；输出仍然**仅是被动制动**，不产生主动推动手柄的力。之后接真实装置时，还需遵守硬件全局限幅和独立保护。
- PC 的 `real/run.py` 与 `common/bridge.py` 都应通过共用的角色控制/状态逻辑获得同一阻力结果，不允许只改一个入口。

## 四、验收与展示

- 使用 Python 标准库实现，优先增加少量清晰的单元测试；保留之前的测试，不要为了新模型悄悄删改关键断言。
- 在**同一固定角度**（例如 `-0.4 rad`）和速度下输出时间序列，证明三个示例人物分别按参数缓升，且 `demo` 立即达到 V0.1 目标。
- 检查时间 `dt=0`、不同更新间隔、阻力降低/自由区、角色切换、状态暂停/恢复、数据过期和故障以及被动功率约束。
- 用简单 CSV 或终端表说明曲线即可；如环境已有绘图库，可画一张对照图，但**不是完成的必要条件**。
- 最好再次通过 Unity 演示验证人物选择及其在 PC 端的响应曲线；如无法自动测试，保留 Python 证据并给出 Unity 手动操作步骤。
- 避免改动 `tests/unity/` 的演示场景或 VR 同学负责的正式 Unity 项目；必要的纯测试修改保留在 `tests/`。
- 最终交付：清晰的 Python 实现、回归测试、最短 Windows 启动步骤、人物时间常数及测试结果记录。推送 GitHub 并提供提交 SHA，区分**模拟模型验证**与**真实人体/制动器标定**。

## 五、先完成再完善

这版只需要回答三个问题：

1. VR 能否在 Windows 选择不同人物并使 PC 正确加载？
2. 不同人物是否能产生明显且可解释的**不同发力建立过程**？
3. 以上变化是否影响原基线、通信协议与故障停止？

如果这些都通过，**V0.2 就可以交付**。下一次再根据联调进展决定做肌肉疲劳/恢复、策略库，还是优先接实体 STM32。不要为了制作“完美真人模型”把这个阶段无限延长。
