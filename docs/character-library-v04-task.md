## 2. 将人物能力与策略分开

人物资料仍是 `demo` 和 `person_01..03`。年龄、性别和训练背景不直接决定力量或策略。V0.3 的基础阻力、缓升时间常数、疲劳参数保持不变。策略只决定某一时刻使用多少可用抵抗能力。

建议新增一个简洁的 `common/strategies.py`，定义三种策略及少量明确标注的演示参数。先用 PC 本地启动参数，例如 `--strategy balanced|defensive|rhythmic`；默认 balanced。TCP 模拟入口与串口入口共用同一个 BridgeState，不分别复制策略算法。策略在 PC 进程启动时确定，不在比赛进行中热切换。VR 仍发送原人物 ID，无需新字段；如果需要新的 UI 以后再讨论。

### 最小策略

- balanced（均衡）：系数 s=1，严格保留 V0.3 的数学计算与状态行为，作为对照。
- defensive（防守）：平时保留一部分抵抗能力，用户向获胜侧推进到不利位置时逐步提高抵抗占比。示例：在 q_free=0.25 rad 到 q_win≈0.4363 rad（当前 VR 的软件阈值，非物理限位）间，将占比从 0.6 平滑升到 1；越界截断。可用简单线性插值或 smoothstep。q=-theta，基准 M_base 仍按原控制公式，自由区保持 0。防守不意味着超出人物原最大能力。
- rhythmic（节奏）：在有效对抗时间内交替增强和减弱抵抗。示例 4 s 周期、系数在 0.65 到 1 之间平滑周期变化；不要引入突变、随机网络或复杂状态机。采用确定性相位，便于重复比较。
- demo 无论选择哪种策略均绕过策略与疲劳，严格复现旧基础控制。不要把 demo 作为三个新策略的展示人物。

这些系数、周期与阈值是软件演示设置，不是人体实验拟合数据。可根据固定输入的实际试验结果微调，使差异清楚、模型仍易懂；记录最终值及原因。不能据此推断某类年龄/性别人群的对抗行为。

### 计算接口建议

```text
M_base = 原 V0.3 角度控制得到的静态幅值
s = strategy(q, active_time)   # 0 <= s <= 1
M_requested = s * M_base
u = clamp(M_requested / character_max_torque, 0, 1)
f = 既有 FatigueState 按 u 更新
M_eligible = M_requested * (1 - fatigue_loss_fraction*f)
M_output = 既有 StrengthResponse 更新(M_eligible)
tau_brake = 既有 passive_torque(M_output, omega, speed_transition)
```

疲劳的负载代理改为策略请求的幅值比例，使策略降低发力时有机会恢复。balanced 时 s=1，因此仍与 V0.3 精确一致。此代理不是实际肌肉激活、用户实测力或实际制动力矩。策略较低负载可能在长时间后减缓疲劳，不能要求它在每个时刻都比 balanced 的动态输出更低；真正的不变量是 `0 <= M_output <= M_eligible <= M_requested <= M_base`，被动功率非正、原有角色与硬件限制不被提高。

### 时间和状态

- 只在双方输入有效且 running 时推进有效比赛时间；使用实际 now 的 dt。重复调用不增加时间，回退和长间隔不补算；沿用 V0.3 的 0.25 s 连续控制限制或等效明确规则。
- paused：立即 STOP/0、清除发力建立值；保持策略相位，按已有规则恢复疲劳。finished、故障和断联：保持/冻结相位，不继续正常策略计算。waiting：重置相位和新回合疲劳；确认新人物时不继承旧人物策略状态。
- 保留 V0.3 对两次计算之间短暂暂停、故障、遥测曾过期等情况的处理。恢复后人物重新缓升；demo 仍严格原行为。
- PC 本地日志增加生效策略、策略系数、请求阻力、有效比赛时间等必要诊断，保留原 base/eligible/output/fatigue 字段。VR 回包和 STM32 帧不新增字段。串口真实执行仍要求本地安全保护和标定。

## 3. 验证

### A. 固定遥测：将人物能力与行为策略分开

使用同一个人（建议 person_02）和同一固定机械输入，例如 -0.4 rad、-0.2 rad/s，比对三种策略 15～30 s 的输出；追加至少一个低负载/接近边界的角度对照来明确防守响应。展示策略系数、静态目标、请求、疲劳、疲劳后目标和最终输出。加入暂停、继续、waiting 新回合验证。

再用同一策略比较 person_01..03，确保人物参数与策略选择独立；对 demo 和 balanced 保留逐步精确的 V0.3 回归（可用冻结 P3.0 输入或参考函数）。输出一份简短 CSV 和清晰曲线/对照表，记录参数、输入、时间和验证范围。

### B. 可重复闭环：利用 P3.0 模拟器

P3.0 的 0.8 N·m 输入让所有人物到达 -0.55 rad；0.6 N·m 固定序列也较快碰到挡位。本轮不能只用相同过强输入展示“所有人赢了”。

先用少量相同的有限软件施力候选（例如在原允许范围内较低的幅值，结合短时下压、松手、回推），选择能在至少一段时间内保持有效阻力区且不立即饱和的公开测试工况；冻结输入后对三种策略同一人物公平比较。使用实际 `BridgeState` + `SimulatedDevice` 固定步长；可复用 `tests/characters/p3_compare.py` 思路。记录最大推进、到阈值时间（若达到）、回合内阻力、疲劳、角度/速度、是否触及限位及功率。不要为通过试验而改变机械模型、人物能力或胜负阈值；找不到区分度足够的工况则报告限制，不虚构优势。相同机械输入的控制差异与相同用户施力下的闭环差异分别报告。现有被动制动不能主动压回用户，模拟回推力来自模拟用户。

### C. 接回正式 VR（最小复验）

使用配对 P3.0 VR 的 `ArmWrestlingMain.unity`、默认公开 P2-D 人物和原 Network 模式，Windows 本机启动 PC（指定策略）和 `sim.mock_stm32 --manual` 或 `--sequence`。不改正式 C#、资产和 UDP 协议；从 demo/原 balanced 到同一人物的 defensive 或 rhythmic 至少验证代表性回合和 PC 日志。可以用已有自动化工具做最小实际 Editor 复验；如需调整测试脚本，不将测试专用功能引入正式运行依赖。不要以旧 Unity 长方体 Demo 或纯 Python 代替正式场景记录。

如果 Unity 工程正在由其他任务使用或本机无法执行，先完成 A/B，明确 C 未执行，不能因此无限拖延控制开发。
